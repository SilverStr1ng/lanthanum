## 1. 项目目标与交付范围

### 1.1 最终目标

实现一个能够通过 **WebGPU 原生渲染**运行 Cesium 核心业务的引擎版本：在高精度地球上流式显示影像、地形、glTF 和 3D Tiles，支持常用 Entity、交互、拾取及渲染效果，并具备资源管理、性能诊断、异常恢复、自动回归和可发布的软件包。

这里的“实现”必须同时包含：数据正确进入、场景持续更新、GPU 正确绘制、交互结果正确、资源正确释放、失败行为明确。单张截图、一个三角形或一个静态地球只能证明局部能力。

### 1.2 分层交付，避免目标失去边界

| 交付层次 | 对应步骤 | 必须具备的结果 | 可以对外作出的声明 |
| --- | --- | --- | --- |
| 渲染基础原型 | S00—S07 | 真实 GPU 资源、管线、WGSL、命令提交、坐标与地球精度验证 | “WebGPU 后端基础原型” |
| 地球演示版 | S00—S10 | 真正接入 Cesium 场景的影像与地形流式地球 | “WebGPU 地球演示版” |
| MVP | S00—S14 | 地球、地形、glTF、3D Tiles 和异步拾取形成完整使用链路 | “可验证的核心三维能力” |
| Beta | S00—S18 | 常用 Entity、贴地与分类、透明、阴影、后处理、扩展入口 | “已列明支持范围的测试版” |
| 生产 v1 | S00—S21 | 固定三维功能范围通过正确性、性能、稳定性、兼容与发布门槛 | “支持指定三维业务范围的 WebGPU 版本” |
| 扩展兼容版 | S22—S24，且生产 v1 已通过 | 补齐二维、Columbus View、模式转换及约定的剩余上游能力，完成逐项对照 | “相对锁定上游版本的功能覆盖与差异已核验” |

**生产 v1 是本计划的第一个正式发布目标。** S22—S24 是继续向更完整 Cesium 能力覆盖推进的执行阶段。生产 v1 完成不等于所有 Cesium API、第三方插件和任意 GLSL 自定义代码都能零修改运行。

### 1.3 默认范围

| 范围项 | 生产 v1 要求 | 后续要求或明确边界 |
| --- | --- | --- |
| 平台 | 桌面浏览器、真实 GPU、三维场景 | 移动端另立设备与功耗预算 |
| 地理能力 | WGS84、ECEF/局部坐标、相机、时钟、高精度与地形遮挡 | 保持上游 CPU 数学语义 |
| 地球数据 | 椭球、影像层、地形、LOD、缓存与请求调度 | 网络服务适配器逐项列入矩阵 |
| 模型 | glTF 2.0 常用 PBR、动画、实例化及指定扩展 | 具体扩展清单在 S00 冻结 |
| 3D Tiles | 直接 glTF 内容、b3dm/i3dm/pnts/cmpt、外部 tileset、隐式切片、特征属性与样式 | 新版或实验性扩展单独列项，不因能解析 JSON 就算支持 |
| 业务对象 | 常用 Entity、Primitive、点线面、标牌与文字、GeoJSON/CZML/KML 基础流程 | 各图元及数据源选项必须有测试编号 |
| 交互 | 相机控制、定位、跟踪、选择、高亮、异步对象与位置拾取 | 同步 GPU 读回接口存在迁移差异 |
| 渲染效果 | 基础大气与雾、常用透明、阴影、抗锯齿、指定后处理、裁剪和分类 | OIT 能力分级需明确，不能用排序透明冒充等价 |
| 自定义着色器 | WebGPU 的受控扩展入口；明确 GLSL 兼容子集与替代办法 | 不承诺任意第三方 GLSL 自动兼容 |
| 二维及特殊能力 | 不作为生产 v1 的前置门槛 | S22—S24 补齐并验收 |
| GI、复杂体积云、GPU 驱动渲染 | 保留必要扩展点 | 基础引擎验收后独立立项 |

本计划暂不规定具体团队规模、预算和日历交付日。先完成基线审计，再依据实际代码与硬件条件估算；不能把 AI 生成代码的速度当作引擎验证速度。

## 2. 已核实事实与技术路线

### 2.1 已核实的起点

1. 官方已发布 CesiumJS 1.147；本计划把该发布标签解析到了上面的完整 commit，避免使用持续变化的 main 作为验收基准。[R1] [R2]
2. 从 1.146 起，部分数学、几何、时间和基础工具已拆入 `@cesium/core`。这不表示整个 `packages/engine/Source/Core` 都被搬走，具体模块位置应以锁定源码为准。[R3]
3. 1.147 的 `Context` 仍创建 WebGL 上下文；`ShaderSource` 会组合 GLSL、内建函数和自动 uniform。迁移工作包含资源创建与着色器生成语义，不能仅替换 draw 调用。[R4] [R5]
4. `Scene.pickAsync` 已存在，应优先沿用其公开语义；`pickPosition` 等同步入口必须另外设计 WebGPU 兼容方式。[R6]
5. 官方 `CustomShader` 接受 GLSL，自定义 shader 兼容性不能视作普通 JavaScript API 兼容性的一部分自动完成。[R7]
6. 已有非官方 WebGPU fork 可供比较，例如 `kurtyoung-dev/cesium-webgpu`。其 README 自述仍为 Beta、未提供生产支持。本计划只把它作为 S00 的评估候选，未对其完成度、性能或正确性作独立认证。[R8]

### 2.2 推荐路线

采用“**保留 Cesium 上层语义，建立后端边界，按可运行功能逐块迁移**”的路线。

先复用坐标计算、相机、请求调度、解析器、瓦片选择、实体系统等已有逻辑。对其中包含 GPU 创建行为的部分抽离接口，再让 WebGL2 与 WebGPU 分别实现资源、管线和 pass 执行。

核心 shader 使用明确的 WGSL 模块与变体生成机制。转换工具可以帮助迁移受控代码，但不能承担所有宏、自动 uniform、派生命令和用户 GLSL 的兼容承诺。

这是一项基于源码结构提出的工程方案，不是官方已提供的 WebGPU 接入接口。

### 2.3 建设顺序原则

- 首先获得可运行的最小链路，随后尽早接入实际 Cesium 地球对象。
- 每增加一类能力，同时补上更新、深度、拾取和释放路径。
- 渲染正确性先达到同等功能的基线，再做 compute、批处理和间接绘制优化。
- 地形与 3D Tiles 的 CPU 调度先保持原行为，避免同时重写调度和渲染导致问题难以定位。
- 接口抽象只覆盖已有迁移需求；初期采用明确的 pass 列表与资源读写声明即可。
- 维持 WebGL2 对照路径可运行，作为回归参照和适当的整场景回退选择。

## 3. 架构边界与兼容性约定

### 3.1 模块改造地图

下表中的“拟新增”名称是建议命名，不表示官方已有这些类。

| 层次 | 主要关注模块 | 建议处理 |
| --- | --- | --- |
| CPU 基础能力 | `packages/core/Source` 中的坐标、矩阵、时间等 | 尽量复用；GPU 上传前才编码成适合传输的数据 |
| 请求与地形数据 | `packages/engine/Source/Core` 中相关调度、编码、provider | 保持调度与解码语义，拆分 GPU 上传职责 |
| 场景与可见性 | `Scene`、`FrameState`、Globe、Model、Tileset | 维持场景更新与 LOD；输出后端可理解的描述 |
| 资源与命令 | Context、Buffer、Texture、VertexArray、DrawCommand | 拟新增后端资源工厂和命令描述；逐步清除上层对 WebGL 包装对象的依赖 |
| 材质与 shader | ShaderSource、AutomaticUniforms、DerivedCommand、Model pipeline | 共用功能描述与数据语义；分别生成 GLSL/WGSL |
| GPU 执行 | 拟新增 `WebGPUBackend`、`PipelineCache`、`PassScheduler` | 管理 device、资源、绑定、render/compute pass 与提交 |
| 应用与 Widget | Viewer、选中、跟踪、事件、数据源 | 处理异步初始化及拾取差异，保持已声明的操作行为 |

Context 与 shader 耦合的直接源码依据见 [R4] [R5]；地形与模型资源创建的进一步审计入口见 [R9] [R10]。实际落地目录和拆分方式由 S03 的架构记录确认。

### 3.2 后端接口应覆盖什么

至少覆盖以下职责，而不仅是一个 `draw()`：

- 设备能力查询与上下文生命周期。
- Buffer、Texture、Sampler、渲染附件的创建、更新与释放。
- 顶点布局、绑定布局、管线描述及缓存。
- Draw/Compute/Copy/Readback 的命令与依赖关系。
- Shader 变体、自动参数、深度及拾取派生能力。
- 每帧统计、错误诊断、资源账本和设备恢复。

建议按更新频率划分 frame/view/material/object 参数，并以共用 schema 生成 CPU 打包代码与 WGSL 声明。WGSL 的布局约束需要单独处理，不能直接沿用 JavaScript 对象布局或假设 GLSL uniform 布局等价。[R11]

### 3.3 必须提前冻结的契约

| 契约 | 默认决策 | 验收责任步骤 |
| --- | --- | --- |
| 初始化 | 新的异步创建入口负责准备 WebGPU；现有同步 Viewer 入口保持既有 WebGL 行为或明确报错 | S02、S03、S21 |
| 后端选项 | 拟定义 `auto / webgpu / webgl2`；强制 WebGPU 失败必须可见 | S02 |
| 回退 | context 创建前优先完成选择；运行中回退重建 canvas/渲染器并恢复明确的应用状态 | S02、S20 |
| 拾取 | 沿用 `pickAsync`；为深度位置与其他 GPU 读回入口提供明确异步替代 | S14、S16 |
| 不支持功能 | 在调用处报明确诊断，或按发布矩阵整场景选择 WebGL2 | 所有步骤 |
| 设备能力 | 区分必需、可选、降级；以实际申请得到的 device 能力为准 | S02、S04 |
| 坐标与深度 | 明确投影、NDC、framebuffer、纹理与 CSS 坐标转换 | S05、S07 |
| 更新模式 | 异步资源、管线及拾取完成能够唤醒 `requestRenderMode` | S06 起持续验证 |
| 扩展接口 | 不把新的原始 GPU 句柄散布到上层业务 API | S03、S18 |
| 多实例 | 资源缓存与能力状态按 device/context 隔离，审计旧全局 ContextLimits 等状态，避免后端互相污染 | S04、S20 |
| 颜色与 alpha | 固定纹理解码、线性光照、sRGB 输出、预乘 alpha 与 HDR/色调映射的转换位置 | S04、S11、S17 |

HTML canvas 在绑定一种 context 后，不能直接改成另一种 context。[R12] WebGPU 读回采用异步映射机制。[R13] 因此上述回退与拾取设计是迁移边界，不能通过悄悄修改返回值或返回过期缓存来掩盖。

所谓回退默认是**整个 Viewer/场景选择另一后端**；不得在 WebGPU 场景中偷偷用第二个 WebGL canvas 绘制尚未迁移的部分，再宣称该功能已原生支持。

## 4. 统一验收规则与测试场景

### 4.1 所有步骤共同的完成定义

每一步只有同时满足以下条件，状态才能由“进行中”改为“已验收”：

- [ ] 该步列出的交付物已进入版本管理，具备明确 commit。
- [ ] 该步专用完成标准全部通过；测试编号与运行命令可以复现。
- [ ] 涉及绘制时，至少在指定真实 GPU 上运行，不能只凭 mock 或 shader 编译成功判定。
- [ ] 对应 WebGL2 基线回归通过，或存在经审查记录的预期差异。
- [ ] 没有未解释的 JS 异常、未处理 Promise 拒绝或 WebGPU validation error。
- [ ] 支持范围、错误行为、资源释放、异步取消和当前限制已写入文档。
- [ ] 报告说明“已完成、未完成、证据、风险、下一步”，不能仅提供代码行数和截图。

不适用项必须说明原因。依赖项未通过时可以并行准备后续代码，但后续步骤不能正式验收。

### 4.2 测试资产包

所有用于正式验收的数据应可合法分发或可在受控环境复现。核心回归不能依赖私人 token、实时在线资产变化或第三方服务稳定性。

| 编号 | 固定场景 | 主要验证内容 |
| --- | --- | --- |
| T00 | 三角形、非对称立方体、四色纹理、深度层、实例化网格 | 坐标方向、剔除、布局、纹理、管线状态 |
| T01 | 椭球与本地编号影像瓦片，至少含地理与 Web Mercator 测试集 | 地球、影像投影、日期变更线、层叠与 LOD |
| T02 | 已知地形瓦片、相邻 LOD、缺失瓦片、山地与海岸剖面 | 地形解码、接缝、过渡、遮挡、父级替代 |
| T03 | glTF 功能样例：PBR、alpha、动画、skin、morph、压缩与实例 | 模型渲染与指定扩展 |
| T04 | 可控 3D Tiles：ADD/REPLACE、外部/隐式切片、各内容类型、metadata | 选择、请求、资源缓存、属性、样式与拾取 |
| T05 | 点线面、Billboard、Label、贴地、裁剪、分类、动态 Entity | 常见 GIS 业务闭环 |
| T06 | 遮挡、透明、地形与模型重叠的拾取场景 | ID、深度位置、异步结果时效 |
| T07 | 两个混合后端 Viewer、反复创建销毁、resize、错误注入 | 隔离性、恢复和泄漏 |
| T08 | 固定城市轨迹，建议约 100 万—300 万可见三角形的中档数据 | 正式性能、流式停顿与内存预算 |
| T09 | 二维、Columbus View、morph 与特殊功能样例 | 扩展兼容阶段 |

T08 的规模是选取样本的建议，不是未测量的真实性能承诺。S01 必须记录实际的资产 hash、可见三角形、draw 数、纹理量、瓦片数和相机轨迹；之后不能通过偷偷减少内容来满足性能要求。

### 4.3 正确性判定口径

**几何与数值：**

- T00 使用解析结果或 CPU 参考值验证，错误的遮挡顺序、剔除、对象 ID 一律不接受。
- 精度测试采用至少 6 个地理位置，包括赤道、正负高纬及日期变更线两侧；测试高度覆盖约 5 m、100 m、10 km、500 km 与 20,000 km。
- 对合成、可见且未接近投影奇点的控制点，GPU 投影相对 CPU 双精度参考的最大屏幕误差目标为 **0.5 px**。
- 上述门槛测量渲染数值误差，不把地形数据误差、资产测量误差、LOD 差异混入其中。

**图像：**

- 固定时间、光照、相机、数据、字体和渲染尺寸；基础测试关闭随机效果与不必要的后处理。
- T00：至少 99.5% 的有效像素，其单通道绝对误差不超过 3/255。
- 复杂静态场景：建议以 SSIM ≥ 0.98、显著差异像素比例 ≤ 1% 为初始门槛；显著差异定义为任一 RGB 通道误差 > 10/255。
- 只有事先登记的区域可以遮罩；标牌、文字、边缘、透明和拾取另有专用测试，不能全部遮掉来过关。
- 无论总分多高，缺瓦片、穿透、错误对象 ID、明显接缝和几何漂移都判失败。
- 对合理的后端光栅化差异保留差异图和解释；变更阈值要在下一轮测试前记录理由，不能事后放宽以掩盖问题。

以上数值是本项目建议的验收预算，不是 Cesium 或 WebGPU 的官方保证。

## 6. 逐步实施任务 S00—S24

### S00：锁定基线，定义范围和复用策略

**前置依赖：** 无。

**实施工作：**

1. 以推荐的 1.147 commit 建立工作分支；若已有工程必须基于另一版本，记录选择理由及与 1.147 的差异。
2. 枚举渲染能力、公开 API、数据格式、glTF 扩展、shader 入口、浏览器平台和关键业务场景。
3. 对每项标记：原生支持、需适配、计划延后、明确不支持；附目标步骤与测试编号。
4. 对非官方 WebGPU fork 做限时可运行性检查与差异审阅，决定整体采用、局部借鉴或不采用；所有复用保留来源和许可证。
5. 明确实验性 API、同步 GPU 读回、第三方插件与专有 SDK 的兼容范围。

**交付物：** `baseline.md`、`compatibility-matrix.md`、`adr/0001-migration-scope.md`。

**完成标准：**

## 7. 性能、稳定性与发布门槛

### 7.1 测量方式

以下均为**建议的项目预算**，S01 应结合实际目标机器和数据确认。未冻结条件的测试可以用于探索，不能用于正式验收。

- 主基准：1920×1080 实际 framebuffer、DPR 1、固定画质、固定 T08 数据和轨迹。
- 热稳态：预热 30 秒，采集 120 秒，重复至少 3 轮；每轮分别报告 p50/p95/p99。
- 冷启动：独立清理所约定的 HTTP/应用缓存并重建 Viewer，重复至少 5 次；管线驱动缓存是否可清理必须注明。
- CPU 更新、CPU 编码提交、rAF 帧间隔与可用的 GPU 时间分别记录。
- GPU 时间只在 device 开启了相应计时能力且采样正确时报告。
- 不在常规帧循环中逐帧等待 `mapAsync` 或队列完成，以免把程序人为串行化。
- 与 WebGL2 比较时，数据、SSE、光照、阴影、透明、分辨率和相机必须一致。
- rAF 受到刷新率与浏览器调度影响；高刷新率或非标准显示模式须单独解释。

### 7.2 建议数值预算

| 指标 | 生产 v1 初始目标 | 验收说明 |
| --- | --- | --- |
| 热稳态帧间隔 | T08 的 p95 ≤ 33.3 ms；目标中位数约 16.7 ms | 60 Hz 环境中中位数采用 ≤ 17.5 ms 的调度容差，不以此证明 GPU 耗时 |
| CPU 更新+编码 | p95 ≤ 10 ms | 分项记录，确认瓶颈；每轮均需达标 |
| 相对回归 | 同画质同内容下，关键 CPU/p95 帧间隔相对 WebGL2 不恶化超过 10% | 若基线本身低于目标性能，仍要单独满足绝对预算或公开调整产品档位 |
| 热稳态卡顿 | 无引擎产生的 > 100 ms 单次主线程任务 | > 50 ms 的任务保留归因；系统外部干扰注明 |
| 本地核心场景首个有意义画面 | T01 在约定本地服务条件下 ≤ 3 s | 包括引擎与 GPU 初始化；单独报告数据请求时间 |
| 本地城市首个可交互工作集 | T08 在相同条件下 ≤ 5 s | 允许正确父级 LOD，但工作集、SSE 与“可交互”必须在 manifest 中预先定义 |
| 普通点击拾取 | 正常负载下 p95 ≤ 100 ms | 不包括主动取消的请求；同时验证队列上限与结果时效 |
| 近地位置拾取 | 合成场景、相机到命中点 ≤ 1 km 时，误差目标 ≤ 0.1 m | 不用于宣称真实地形资产具有 10 cm 测量精度 |
| 引擎估算 GPU 资源 | T08 建议稳态 ≤ 768 MiB | 这是引擎账本，不是浏览器可精确读取的物理显存；按 S01 设备调整并冻结 |
| CPU/网络缓存与在途工作 | S01 为 T08 分别冻结字节、请求数、解码数和上传队列上限 | 超限触发背压或淘汰；CPU 缓存与 GPU 驻留量不合并成一个模糊“内存”数字 |
| 资源长期增长 | 同轨迹稳定缓存后，最后 10 圈资源账本相对首个稳定窗口增幅 ≤ 5% | 同时检查对象数量、峰值、淘汰与销毁；不能只看 JS heap |
| 长时运行 | T08/T07 组合连续 2 小时 | 无未处理异常、失控重试、持续内存增长或严重视觉错误 |

上述数值首先适用于主验收机。其他认证设备必须有单独冻结的分辨率、画质和性能档位；未通过主档位的设备不能宣称具有同等性能。

预算不达标时，应分析瓶颈、调整实现或正式重新定义产品档位。不得只减小窗口、关闭效果或删掉高负载资产而保留原有性能声明。

### 7.3 平台与发布检查

生产 v1 至少要求：

- [ ] 三个真实硬件配置通过，其中包含一台独立显卡、一台集成显卡或统一内存设备。
- [ ] 至少覆盖两个 GPU 厂商和两个目标操作系统；可以通过三台设备满足。
- [ ] WebGPU 原生认证覆盖至少两个浏览器引擎，例如 Chromium 与 WebKit/Gecko 中实际可运行的目标组合。
- [ ] 记录准确浏览器版本与能力快照；Chrome 与 Edge 不算两个独立浏览器引擎。
- [ ] 浏览器具有接口但设备不可用、功能不足或仅软件适配器的情况另列，不冒充硬件认证。
- [ ] 所有公开支持的平台通过必需回归；其他组合只能标为未认证或回退。
- [ ] 生产三维矩阵的必需项全部通过，不存在“代码写了但没测”的支持项。
- [ ] 冷/热启动、拾取、设备恢复、销毁与异常数据都通过。
- [ ] 发行产物中的 WebGL2 回退路径仍可用；数据来源署名没有因新后端而消失。本期默认交付双后端包，按需裁剪的单后端构建可另立优化任务。
- [ ] 发布包、类型定义、示例、迁移说明、许可证与已知限制完整。

具体浏览器版本会变化，因此本计划不把某个版本号写成永久支持结论；验收以实际目标环境为准。

## 8. 执行方式、进度与风险管理

### 8.1 每轮工作方式

建议以 1—2 周为一个检查节奏，而不是要求每个大步骤都能在两周内结束。

每轮选择一个可验收的纵向任务，例如“带 MASK 的 glTF 同时正确参与颜色、深度和拾取”。任务过大时拆小，但每个子任务仍要有输入、输出、测试与限制。

常规流程：

1. 读取前置步骤、支持矩阵与相关 ADR。
2. 明确本轮只解决的功能和验收用例。
3. 实现最小闭环，运行相关回归。
4. 做集成审查，更新支持矩阵和进度报告。
5. 通过 gate 后合入集成主线，保留可回退提交。
6. 根据剩余风险安排下一轮，不因出现新视觉想法就替换迁移主线。

### 8.2 可以并行的工作

| 工作流 | 可并行内容 | 汇合要求 |
| --- | --- | --- |
| 后端与 shader | S04—S07 的资源、布局、变体与数值工具 | 共用数据 schema、深度约定和 pipeline key |
| 地球与模型准备 | G2 期间准备 glTF 样例、扩展矩阵与 loader 审计 | 模型正式验收仍依赖资源和精度 gate |
| 业务与交互 | Entity 样例、数据源测试、Widget 调用梳理 | 依赖 S14 的异步语义 |
| 验证与诊断 | 基线采集、平台测试、资源统计 | 从 S01 开始持续工作 |

不要让多个执行者同时自行定义坐标规则、绑定布局或 shader 接口；这些属于共享契约，应先落到 ADR。

### 8.3 进度计算

生产 v1 和扩展兼容版分别统计，不能用一个数字混合。

同时分别报告三个维度：WebGPU 原生功能覆盖率、已通过的浏览器/硬件组合、公开 API 的语义兼容情况。每个分母在 S00 冻结；破坏性变化逐项展示，不能用总体比例掩盖。

`生产 v1 完成度 = 已验收任务的固定权重之和 / 生产 v1 总权重`

任务状态建议为：未开始、进行中、待验收、已验收、阻塞。未通过验收的“代码完成”不获得完成权重。

本文件没有审查现有实现，因此不对当前代码给出虚构的完成百分比。实际起点由 S00/S01 确认。

### 8.4 每轮报告模板

- 已验收内容：

### 8.5 主要风险及处理

| 风险 | 早期信号 | 处理与负责步骤 |
| --- | --- | --- |
| shader 组合失控 | 进入新视角持续编译、变体键不断增长 | S06 冻结功能维度；S19 预热与限流 |
| 地球精度问题拖到后期 | 高空正常、地面抖动或深度错误 | S07 独立 gate，未通过不宣布地球基础完成 |
| 公共 API 名称相同但行为变了 | 旧同步调用得到 Promise/过期值 | S00/S14 明确契约与迁移示例 |
| 启动卡顿 | 大批解码、纹理上传、shader 编译同步发生 | S01 起测量，S12/S19 分帧与并发预算 |
| 数据不断加载卸载 | 缓存预算、引用计数或取消语义失效 | S10/S13/S20 生命周期压力测试 |
| 过早引入复杂新算法 | 基础模型未完成就开始 GI/大规模 GPU culling | 回到已冻结 gate，增强需求独立排期 |
| 上游更新难以合并 | 大量无关重构、全仓改语言或改变公共行为 | 限定差异、保留 WebGL2、S21 演练合入 |
| 演示成功但无法发布 | 仅一台机器能跑、没测异常和打包 | S20/S21 硬性恢复与发行门槛 |
| “全部兼容”范围无限增长 | 不断把新上游版本纳入当前分母 | S00 锁定版本，新增版本单独规划 |

### 8.6 排期方法

S00—S01 完成后，为每一步估算乐观、常规、保守三种工作量，并明确可并行部分。S07 和 S14 是重新估算的重要节点：前者揭示精度与后端设计风险，后者揭示公共 API 与交互迁移成本。

计划排期必须包含真实 GPU 调试、跨平台回归、资产准备、集成冲突和文档迁移。若资源有限，先交付明确范围的 MVP，再推进生产 v1；不得把后续阶段从文档中删掉后称为完整 Cesium。
